# Large Language Models

---

## 1. Definition and Fundamental Concepts

**What is an LLM?**
A Large Language Model is a neural network (almost always a Transformer) trained on huge amounts of text to predict the next word (token) in a sequence. Because it sees billions/trillions of words during training, it ends up learning grammar, facts, reasoning patterns, and even coding ability — all as a side effect of getting good at "predict the next token."

**Why "Large"?**
- **Large data**: trained on trillions of tokens (web text, books, code, papers).
- **Large parameters**: modern LLMs range from a few billion to hundreds of billions of parameters.
- **Large compute**: trained on thousands of GPUs/TPUs for weeks or months.

**Core idea in one line:** An LLM is a giant probability machine — given some text, it outputs a probability distribution over "what token comes next," and it repeats this to generate full sentences.

**Key properties that make LLMs special:**
- **Emergent abilities**: capabilities like arithmetic, chain-of-thought reasoning, or in-context learning appear only after the model crosses a certain scale — they weren't explicitly programmed.
- **In-context learning**: the model can learn a new task from a few examples given in the prompt, without updating any weights.
- **General purpose**: one model can do translation, summarization, coding, Q&A, etc.

---

## 2. Generative Models

A **generative model** learns the underlying distribution of data so it can *create* new samples that look like the training data (as opposed to a **discriminative model**, which only learns to separate classes, e.g., spam vs not-spam).

- Discriminative: models P(y | x) — "given this input, what's the label?"
- Generative: models P(x) or P(x, y) — "what does realistic data look like, and can I sample new data from it?"

LLMs are generative models over text: they model P(next token | previous tokens), and by sampling repeatedly, they generate entire passages, code, or conversations.

Other generative model families (good to know for contrast in interviews):
- **GANs** (Generative Adversarial Networks) — generator vs discriminator game, mostly used for images.
- **VAEs** (Variational Autoencoders) — learn a compressed latent space and decode from it.
- **Diffusion models** — learn to reverse a noising process (used in image gen like Stable Diffusion).
- **Autoregressive models** (GPT-family) — generate one token at a time, conditioned on everything generated so far. This is the LLM approach.

---

## 3. GPT (Generative Pre-trained Transformer)

GPT is OpenAI's family of autoregressive, decoder-only Transformer models. The name tells you the recipe:
- **Generative**: it generates text token by token.
- **Pre-trained**: first trained on a huge unlabeled text corpus using self-supervised next-token prediction.
- **Transformer**: uses the Transformer architecture (specifically, only the *decoder* stack, with masked self-attention so a token can only look at earlier tokens, never future ones).

**How GPT works at a high level:**
1. Input text is tokenized into sub-word tokens.
2. Each token is converted into an embedding vector, and positional information is added.
3. The embeddings pass through many stacked decoder blocks (masked self-attention + feed-forward layers).
4. The final layer produces a probability distribution over the vocabulary for "what's the next token."
5. A token is sampled/selected, appended to the sequence, and the process repeats (autoregressive generation).

**Evolution (conceptually, not exact specs):** GPT-1 proved pretraining + fine-tuning works for language. GPT-2 showed that scaling up produces surprisingly fluent, general text generation. GPT-3 showed strong in-context/few-shot learning at scale. GPT-3.5/4 and beyond added instruction tuning, RLHF alignment, and multi-modal capability.

---

## 4. Transformers

The Transformer (Vaswani et al., 2017, "Attention Is All You Need") is the backbone architecture of nearly all modern LLMs. It replaced RNNs/LSTMs because it processes tokens **in parallel** instead of sequentially, and it captures long-range dependencies much better.

**Two main pieces:**
- **Encoder**: reads the whole input and builds a contextual representation of it (used in BERT — good for understanding tasks).
- **Decoder**: generates output one token at a time, attending to previous tokens (used in GPT — good for generation tasks).
- Some models use both (encoder-decoder, e.g., T5, the original Transformer for translation).

**Self-Attention (the key mechanism):**
For every token, the model computes three vectors: **Query (Q)**, **Key (K)**, **Value (V)** — all derived from the token's embedding via learned weight matrices.

Attention score between token i and token j:
```
Attention(Q, K, V) = softmax( (Q · K^T) / sqrt(d_k) ) · V
```
Intuition: "How relevant is token j to understanding token i?" The softmax turns raw scores into weights that sum to 1, and we take a weighted average of all Value vectors. This lets every token directly "look at" every other token, regardless of distance — solving the long-range dependency problem RNNs struggled with.

Why divide by `sqrt(d_k)`? Without scaling, dot products grow large as dimension increases, pushing softmax into regions with tiny gradients. Scaling keeps training stable.

**Multi-Head Attention:** Instead of one attention computation, the model runs several (e.g., 12, 16, 96) attention "heads" in parallel, each with its own Q/K/V projections. Each head can specialize (one head might track syntax, another might track coreference like "it" → "the dog"). Outputs from all heads are concatenated and projected back.

**Masked Self-Attention (decoder-only, GPT-style):** A mask ensures token *i* can only attend to tokens ≤ i, never future tokens. This is essential for autoregressive generation — the model must not "cheat" by seeing the answer.

**Feed-Forward Network (FFN):** After attention, each token's representation passes through a small 2-layer MLP (same weights applied to every position) that adds non-linearity and extra capacity.

**Residual connections + Layer Normalization:** Every sub-layer (attention, FFN) has a skip connection (`x + Sublayer(x)`) followed by normalization. This prevents vanishing gradients and lets us stack very deep networks (dozens/hundreds of layers).

**Why Transformers beat RNNs/LSTMs:**
| RNN/LSTM | Transformer |
|---|---|
| Sequential processing (slow, no parallelism) | Fully parallel over sequence |
| Struggles with long-range dependencies | Self-attention connects any two tokens directly |
| Vanishing gradient over long sequences | Residuals + attention avoid this |
| Fixed hidden state as "memory bottleneck" | No bottleneck — attends to full context |

## 5. Transfer Learning

Transfer learning means taking knowledge learned on one task/dataset and reusing it for a different but related task, instead of training from scratch.

In NLP/LLMs, this happens in two stages:
1. **Pretraining**: Train a big model on a massive general corpus (Wikipedia, books, web) using a self-supervised objective (next-token prediction, or masked-token prediction). The model learns general language understanding — grammar, facts, reasoning patterns.
2. **Fine-tuning/adaptation**: Take that pretrained model and adapt it to a specific downstream task (e.g., sentiment classification, medical Q&A, chat assistant) using a much smaller labeled dataset.

**Why it works:** Language has universal structure (syntax, semantics, world knowledge) that's useful across almost any task. Instead of every task learning language from zero, we reuse the expensive general knowledge and only spend cheap compute adapting to the specific task.

**Analogy:** It's like hiring someone who already knows how to read and write fluently (pretraining), then giving them a short on-the-job training for your specific role (fine-tuning) — much faster than teaching them to read from scratch.

---

## 6. Fine-Tuning

Fine-tuning = continuing to train a pretrained model on a smaller, task-specific (often labeled) dataset so it specializes.

**Types of fine-tuning:**
- **Full fine-tuning**: update *all* model parameters. Best performance ceiling but expensive (needs to store gradients/optimizer states for every parameter — memory-heavy) and risks **catastrophic forgetting** (losing general abilities).
- **Instruction fine-tuning (SFT — Supervised Fine-Tuning)**: train on (instruction, ideal response) pairs so the model learns to follow instructions/chat format rather than just "complete the text."
- **PEFT (Parameter-Efficient Fine-Tuning)**: only update a small subset/add-on of parameters (LoRA, adapters, prompt tuning) — covered in detail in Section 16.
- **Domain-adaptive fine-tuning**: continue pretraining (next-token prediction, no labels needed) on domain-specific text (e.g., legal, medical) to shift the model's "vocabulary and style" before task-specific fine-tuning.

**Fine-tuning vs Prompting (in-context learning):** Fine-tuning bakes new behavior into the weights (persistent, needs retraining data + compute). Prompting/in-context learning changes behavior only for that one interaction by giving instructions/examples in the prompt (no weight updates, cheap, but limited by context window and doesn't "stick").

## 7. Language Model (the core concept)

A **language model** is any model that assigns a probability to a sequence of words/tokens, or equivalently predicts the next token given previous ones:

```
P(w1, w2, ..., wn) = P(w1) · P(w2|w1) · P(w3|w1,w2) · ... · P(wn|w1,...,w(n-1))
```

This is the **chain rule of probability** applied to text — the foundation of every autoregressive LLM.

**History (context for interviews):**
- **N-gram models**: estimate P(next word | last N-1 words) via counting frequencies in a corpus. Simple but suffers from data sparsity and no real "understanding."
- **Neural language models (RNN/LSTM-based)**: learn dense representations, better generalization, but sequential and struggle with long context.
- **Transformer-based LLMs**: current state of the art — parallel, long-context, scalable.

**Types by architecture:**
- **Autoregressive / causal LM** (GPT-style): predicts next token left-to-right. Great for generation.
- **Masked LM** (BERT-style): predicts randomly masked tokens using both left and right context. Great for understanding tasks (classification, embeddings), not natural at free-form generation.
- **Sequence-to-sequence LM** (T5, BART): encoder reads input, decoder generates output — good for translation, summarization.

## 8. Tokenization

Tokenization converts raw text into the discrete units (tokens) that a model actually processes as numbers. This is arguably one of the most "gotcha" interview topics.

**Why not use whole words as tokens?**
- Vocabulary would be huge (every inflection, typo, rare word needs its own slot) → huge embedding table, and any unseen word becomes `<UNK>` (out-of-vocabulary problem).

**Why not use single characters?**
- Vocabulary becomes tiny, but sequences become extremely long (a 5-word sentence might be 30 characters), which is computationally expensive and makes it harder for the model to capture meaning per token.

**Solution: sub-word tokenization** — a middle ground. Common words stay as single tokens; rare/complex words get split into meaningful pieces. This balances vocabulary size against sequence length, and elegantly handles unseen words (they get broken into known sub-pieces, so `<UNK>` is nearly eliminated).

### 8.1 Byte Pair Encoding (BPE)
**Used by:** GPT-2, GPT-3, RoBERTa (and byte-level BPE in GPT-4-class models).

**Intuition:** Start from the smallest units (characters, or bytes) and greedily merge the *most frequent adjacent pair* into a new token, repeating until you hit a target vocabulary size.

**Algorithm (working):**
1. Initialize vocabulary as individual characters (or bytes) of the training corpus, and represent every word as a sequence of these characters plus an end-of-word marker.
2. Count all adjacent symbol pairs across the corpus.
3. Merge the most frequent pair into a new single symbol, add it to the vocabulary.
4. Repeat steps 2–3 for a fixed number of merges (this number determines final vocab size).
5. At inference, apply the same learned merge rules to split new text.

**Example:** Corpus has "low", "lower", "lowest" frequently. Start: `l o w`, `l o w e r`, `l o w e s t`. "l"+"o" is frequent → merge to "lo". Then "lo"+"w" → "low". Eventually "low" becomes one token, while "er" and "est" might become separate reusable tokens — so "lower" = ["low", "er"].

**Byte-level BPE** (GPT-2/3/4 use this): operates on raw UTF-8 bytes instead of unicode characters, so literally *any* string (emojis, any language, weird symbols) can always be tokenized — there's never an unknown character.

### 8.2 WordPiece
**Used by:** BERT, DistilBERT.

**Intuition:** Very similar to BPE (also starts from characters and merges pairs), but instead of merging the *most frequent* pair, it merges the pair that gives the **maximum increase in likelihood** of the training data (i.e., merges based on a language-model-score improvement, not raw frequency).

**Working (conceptually):**
1. Start with a base vocabulary of characters.
2. For every candidate merge, score it by how much it increases the likelihood of the training corpus under a unigram LM if that merge is applied.
3. Pick the merge with the highest score, add to vocabulary.
4. Repeat until target vocab size.

**Notation quirk:** WordPiece marks continuation sub-tokens with `##` — e.g., "playing" → `["play", "##ing"]`. The `##` tells you "this piece attaches to the previous one, don't add a space."

**BPE vs WordPiece:** Both are greedy, bottom-up, sub-word methods. Difference is purely the *merge selection criterion* — frequency (BPE) vs likelihood gain (WordPiece).

### 8.3 SentencePiece
**Used by:** T5, ALBERT, XLNet, LLaMA (uses SentencePiece with a BPE or Unigram model underneath).

**Key idea:** SentencePiece is not a new merge algorithm by itself — it's a **tokenization framework** that treats the input as a raw stream of Unicode characters (including spaces!) rather than pre-splitting on whitespace first. It can then run BPE or a **Unigram Language Model** algorithm on top.

**Why this matters:** Traditional BPE/WordPiece assume you can split on spaces first (works for English/European languages). But languages like Japanese, Chinese, or Thai don't use spaces to separate words. SentencePiece solves this by treating spaces as just another character (often replaced with a special symbol `▁`), so the same algorithm works language-agnostically and tokenization is fully reversible (detokenization is exact, no ambiguity about where spaces went).

**Unigram LM tokenization (the other algorithm SentencePiece supports):** Start with a large candidate vocabulary of sub-word pieces, then iteratively remove the pieces that hurt overall corpus likelihood the least, until reaching the target vocab size — this is a "top-down/pruning" approach, the opposite direction from BPE's "bottom-up/merging" approach. It also naturally supports multiple valid segmentations of the same word with probabilities, enabling sampling-based regularization during training.

**Quick comparison table:**
| Method | Direction | Merge/Split Criterion | Handles spaces? | Used by |
|---|---|---|---|---|
| BPE | Bottom-up merge | Most frequent pair | Needs pre-split | GPT-2/3, RoBERTa |
| WordPiece | Bottom-up merge | Max likelihood gain | Needs pre-split | BERT |
| SentencePiece (Unigram) | Top-down prune | Max corpus likelihood retained | Space = character | T5, LLaMA, ALBERT |

**Practical consequences of tokenization choice (interview gold):**
- Tokenizer determines the model's **effective vocabulary size**, which affects embedding table size and softmax output layer size (both scale with vocab size).
- Number of tokens per word affects how much "context budget" text consumes — e.g., rare words or non-English text can use 2-4x more tokens than English, effectively shrinking usable context window for those languages.
- Tokenization artifacts explain weird LLM failures — e.g., difficulty with counting letters or reversing strings, because the model sees "strawberry" as 2-3 sub-word tokens, not individual letters.

## 9. Context Window

The **context window** is the maximum number of tokens (input + output combined, in most architectures) that a model can process/attend to at once in a single forward pass.

**Why it's limited:**
- Self-attention cost grows **quadratically** with sequence length: O(n²) in both compute and memory, because every token attends to every other token. Doubling context length roughly quadruples the attention compute.
- Positional encoding schemes (esp. learned/absolute ones) may also be trained only up to a certain max length.

**Effects of context window size:**
- **Too small:** model "forgets" earlier parts of a long conversation/document — can't do long-document summarization, long codebases, or long multi-turn chats without truncation.
- **Larger context** (e.g., 128K, 1M tokens in newer models) enables long-document QA, whole-codebase reasoning, and long conversations, but at higher compute/memory cost per call, and models can suffer from **"lost in the middle"** — attention tends to weight the beginning and end of context more than the middle, so relevant info buried in the middle of a huge context can be under-utilized even if it's technically "within window."

**Techniques to extend context window (good to mention):**
- **Sparse/local attention** (e.g., sliding window attention) — each token attends only to a local neighborhood instead of everything, reducing cost from O(n²) to roughly O(n).
- **FlashAttention** — an IO-aware exact-attention algorithm that reduces memory reads/writes, making long-context attention much faster without changing the math.
- **RoPE/ALiBi + position interpolation/extrapolation tricks** — extend the useful range of positional encodings beyond what was seen in training.
- **KV-caching** — during generation, cache previous tokens' Key/Value vectors so you don't recompute attention for the whole prefix at every new token (huge speedup for autoregressive decoding, though memory use grows with context length).

## 10. Embeddings

An **embedding** is a dense, fixed-size vector representation of a discrete token (word/sub-word), learned so that semantically/syntactically similar tokens end up close together in vector space.

**How they're created in LLMs:** The model has an embedding matrix of shape `[vocab_size, embedding_dim]`. Each token ID is just a row lookup into this matrix — a learnable table, trained jointly with the rest of the model via backpropagation.

**Why not use one-hot vectors directly?** One-hot vectors are sparse, huge (size = vocab size, e.g., 50,000+), and carry no notion of similarity (every word is equally "different" from every other word). Embeddings compress this into a small dense vector (e.g., 768, 1024, 4096 dims) that encodes meaning — "king" and "queen" end up near each other; the famous `king - man + woman ≈ queen` relationship emerges naturally.

**How embedding size (dimension) affects the model:**
- **Larger embedding dimension:**
  - Can encode richer, more nuanced semantic/syntactic information per token → generally better downstream quality, especially for large vocabularies or complex tasks.
  - Increases parameter count (embedding matrix = `vocab_size × embed_dim`, and this size also propagates through every Transformer layer since hidden size = embedding size in most architectures) → more memory, slower training/inference.
  - Risk of overfitting if the training data isn't large enough to justify the extra capacity.
- **Smaller embedding dimension:**
  - Faster, lighter, cheaper — good for resource-constrained deployment (edge devices, mobile).
  - May underfit / lose the ability to represent fine-grained distinctions between similar words or complex relationships, capping the ceiling on model quality.
- In practice, embedding dimension scales with model size (e.g., GPT-3 small variants use ~768, largest variants use ~12,288) because it's tied to the Transformer's hidden dimension throughout the network — it's not usually tuned in isolation.

**Note — "embeddings" also refers to sentence/document embeddings** (used in RAG/semantic search, which is directly relevant to Sourav's FAISS-based RAG work): here, an entire sentence/passage is mapped to one dense vector (e.g., via a model like `sentence-transformers` or by pooling an LLM's hidden states) so that semantically similar passages have high cosine similarity — this is the backbone of vector search in FAISS/Pinecone/Weaviate.

## 11. Positional Encoding

Self-attention by itself is **permutation-invariant** — it has no built-in sense of word order (it would treat "dog bites man" the same as "man bites dog" without extra info). Positional encoding injects order information into the token embeddings.

**Types:**
- **Sinusoidal (fixed, original Transformer paper):** each position gets a fixed vector built from sine/cosine functions of different frequencies:
  ```
  PE(pos, 2i)   = sin(pos / 10000^(2i/d))
  PE(pos, 2i+1) = cos(pos / 10000^(2i/d))
  ```
  Added directly to token embeddings. Advantage: no extra learned parameters, and it can theoretically generalize to sequence lengths longer than seen in training because it's a smooth deterministic function.
- **Learned absolute positional embeddings** (used in GPT-2, BERT): a trainable embedding table indexed by position (0, 1, 2, ...), added to token embeddings just like sinusoidal ones, but learned via backprop. Downside: cannot generalize beyond the max position seen during training.
- **Relative positional encoding** (Transformer-XL, T5): instead of encoding "absolute position 57," encode the *relative distance* between token i and token j directly inside the attention computation. Better generalization to varying lengths since relationships like "3 tokens apart" matter more than "at position 57" for meaning.
- **RoPE — Rotary Positional Embedding** (LLaMA, GPT-NeoX, most modern open LLMs): encodes position by *rotating* the Query and Key vectors in a multi-dimensional space by an angle proportional to their position, so that the dot product between Q and K naturally depends on the *relative* distance between tokens. Combines benefits of absolute encoding (simple to implement, applied per-token) with relative encoding (captures distance naturally) and extrapolates reasonably well to longer sequences.
- **ALiBi (Attention with Linear Biases):** instead of adding position info to embeddings at all, it directly biases the attention scores by subtracting a penalty proportional to the distance between tokens (farther tokens get a bigger penalty). Very good at extrapolating to sequences longer than training length, with minimal extra compute.

**Interview one-liner:** "Positional encoding gives the Transformer a sense of word order — without it, attention would see a bag of words, not a sequence."

## 12. LLM Training Objective

**Pretraining objective — Next Token Prediction / Causal Language Modeling:**
Given a huge unlabeled text corpus, the model is trained to maximize the likelihood of the actual next token at every position, i.e., minimize **cross-entropy loss** between the predicted probability distribution and the true next token:

```
Loss = - (1/N) * Σ log P(w_t | w_1, ..., w_(t-1))
```

This is fully **self-supervised** — the "labels" are just the next words in the raw text itself, no human annotation needed, which is exactly why it can scale to trillions of tokens scraped from the internet.

**Masked Language Modeling (alternative objective, used by BERT):** randomly mask ~15% of tokens in the input and train the model to predict the masked tokens using both left and right context. Good for building bidirectional understanding representations, but not naturally suited to free-form generation (no clean way to generate token-by-token left-to-right).

**Post-pretraining objectives (the modern LLM pipeline, worth knowing end-to-end):**
1. **Pretraining** — next-token prediction on massive raw text corpus → produces a "base model" (knows language and facts, but not great at following instructions or being safe/helpful).
2. **Supervised Fine-Tuning (SFT)** — same next-token-prediction loss, but on curated (instruction, ideal answer) pairs, often with loss computed only on the "answer" tokens (not on the instruction/prompt tokens) → produces an "instruction-following model."
3. **Alignment (RLHF or DPO)** — further trains the model to prefer responses humans rate as better (helpful, harmless, honest) → produces the final "chat/assistant model." Covered in detail in Section 15.

## 13. Teacher Forcing

**Teacher forcing** is a training technique for sequence models (RNNs and Transformer decoders alike): at each time step during training, instead of feeding the model's own (possibly wrong) previous prediction back in as input for predicting the next token, you feed it the **ground-truth previous token** from the training data.

**Why it's used:**
- Without teacher forcing, if the model makes an early mistake, that wrong token gets fed back in, and errors compound across the sequence — training would be slow and unstable, especially early in training when the model is bad.
- With teacher forcing, every prediction is conditioned on the *correct* history, so the model gets a clean, independent gradient signal for every position in parallel — this is also what makes Transformer training highly parallelizable (you can compute the loss at all positions in one forward pass, since you already have the whole correct sequence).

**The catch — Exposure Bias:** At *inference* time, there's no ground truth to feed back in — the model must condition on its *own* previous predictions. If the model produces an error, that error now compounds during generation (something it never had to deal with during training). This mismatch between training (always sees correct history) and inference (sees its own possibly-wrong history) is called **exposure bias**, and it's one reason generated text can "drift" or degrade over long outputs.

**Mitigations mentioned in literature:** scheduled sampling (occasionally feed the model its own prediction during training to simulate inference conditions), and more robust decoding strategies at inference time (see Section 14).

## 14. Decoding in LLMs (Generation Strategies)

Decoding = the process of turning the model's output probability distribution (over the vocabulary, at each step) into actual chosen tokens, one at a time, to build the final generated text.

### 14.1 Greedy Decoding
At every step, pick the single **highest-probability** token.
- ✅ Fast, deterministic, simple.
- ❌ Often produces repetitive, generic, "boring" text; can get stuck in loops (e.g., "I don't know. I don't know. I don't know."); doesn't explore alternative good sequences — a locally optimal token now can lead to a globally worse sentence.

### 14.2 Beam Search
Instead of keeping only the single best token, keep track of the **top-k partial sequences ("beams")** at every step, expand each, and keep the best k overall by cumulative probability (usually log-probability, summed).
- ✅ Finds higher overall-probability sequences than greedy; good for tasks with a "correct" answer like translation or summarization where you want the most likely coherent output.
- ❌ Computationally more expensive (k times the work); still tends to produce generic/safe/bland text; can suffer from **beam search degeneration** — long outputs sometimes become repetitive because the "safe, average" continuation is often high-probability; not great for open-ended creative generation.
- **Beam width (k)** trade-off: larger k explores more but is slower and, counter-intuitively, doesn't always mean better text quality for open-ended generation (larger beams tend to favor generic short/safe continuations).

### 14.3 Sampling-based methods (for more natural/creative/diverse generation)
Instead of always taking the max, **sample** from the probability distribution — this introduces controlled randomness so outputs feel more natural/human and vary across runs.

**Temperature (T):** rescales the logits before softmax:
```
P_i = exp(logit_i / T) / Σ exp(logit_j / T)
```
- **T = 1**: unchanged distribution (standard).
- **T < 1** (e.g., 0.3): sharpens the distribution — high-probability tokens become even more likely, low ones nearly vanish → more focused, deterministic, "safe" output (closer to greedy as T→0).
- **T > 1** (e.g., 1.5): flattens the distribution — makes low-probability tokens more competitive → more diverse, creative, but riskier (more likely to produce nonsense) output.
- Temperature doesn't remove any tokens from consideration — it only reshapes how "peaked" or "flat" the probabilities are.

**Top-k Sampling:** Restrict sampling to only the **k most probable tokens** at each step (e.g., k=40), renormalize their probabilities, then sample from just that shortlist.
- ✅ Cuts off the long, unlikely "tail" of the vocabulary that could produce garbage.
- ❌ Fixed k is a blunt instrument: sometimes the "true" set of reasonable next tokens is much smaller than k (distribution is very peaked — e.g., after "The capital of France is", almost all probability is on "Paris") and top-k still allows some noise in; other times the reasonable set is much larger than k (distribution is very flat — many plausible continuations) and top-k cuts off valid options.

**Top-p (Nucleus) Sampling:** Instead of a fixed count, choose the **smallest set of tokens whose cumulative probability exceeds a threshold p** (e.g., p=0.9), renormalize, and sample from that dynamic set.
- ✅ Adapts to the shape of the distribution at every single step — when the model is very confident (peaked distribution), the nucleus is small (maybe just 1-2 tokens); when the model is uncertain (flat distribution), the nucleus naturally grows to include more candidates. This generally produces more coherent yet diverse text than fixed top-k.
- This is why top-p is the most commonly used default sampling strategy in modern chat LLMs, often combined with a moderate temperature.

**Practical combo used in production:** Most systems apply **temperature + top-p (and sometimes top-k as an extra safety cap)** together — e.g., temperature=0.7, top_p=0.9 — to balance coherence and creativity. For deterministic/reproducible tasks (code generation, factual QA), lower temperature or even greedy decoding is preferred; for creative writing/brainstorming, higher temperature + top-p is preferred.

**Quick comparison table:**
| Method | Deterministic? | Main strength | Main weakness |
|---|---|---|---|
| Greedy | Yes | Fast, simple | Repetitive, suboptimal globally |
| Beam Search | Yes | Higher-probability full sequences | Generic/bland, expensive |
| Temperature sampling | No | Controls randomness smoothly | Doesn't limit tail risk alone |
| Top-k | No | Cuts unlikely tail | Fixed k not adaptive to context |
| Top-p (nucleus) | No | Adapts dynamically to distribution shape | Slightly more complex to tune |

## 15. Quantization

**Quantization** reduces the numerical precision used to store/compute model weights (and sometimes activations) — e.g., from 32-bit floating point (FP32) down to 16-bit (FP16/BF16), 8-bit integers (INT8), or even 4-bit (INT4).

**Why it matters:** A 7-billion-parameter model in FP32 needs ~28 GB just for weights; in FP16 that's ~14 GB; in INT8 ~7 GB; in INT4 ~3.5 GB. Quantization is often the difference between "needs a data-center GPU" and "runs on a laptop/phone."

**Benefits:**
- Smaller memory footprint (model fits on cheaper/smaller hardware, or you can fit larger models on the same hardware).
- Faster inference (integer/low-bit math is cheaper, and less data movement between memory and compute units, which is often the real bottleneck).
- Lower energy/cost for deployment at scale.

**Trade-off:** Precision loss can degrade output quality — the risk grows as you go to lower bit-widths (INT4 riskier than INT8). Good quantization techniques try to minimize this quality loss.

**Common approaches (good for interviews):**
- **Post-Training Quantization (PTQ):** quantize an already-trained model's weights, no retraining needed — fast and simple, but can lose more accuracy, especially at very low bit-widths.
- **Quantization-Aware Training (QAT):** simulate quantization effects *during* training/fine-tuning so the model adapts its weights to be robust to the reduced precision — better final quality, but needs more compute/data.
- **GPTQ, AWQ, GGUF/GGML formats:** popular practical quantization schemes/formats for deploying open LLMs (e.g., LLaMA) efficiently on consumer hardware.
- **Mixed precision:** keep sensitive parts of the model (e.g., certain layers, or activations) at higher precision while quantizing the bulk of the weights — balances speed/size with quality.

**Connects directly to QLoRA** (Section 16) — QLoRA fine-tunes a *quantized* (4-bit) base model using LoRA adapters kept in higher precision, dramatically reducing the GPU memory needed to fine-tune large models.

## 16. Knowledge vs Behavior (LIMA — "Less Is More for Alignment")

This is a subtle but important conceptual distinction that interviewers love to probe:

- **Knowledge** (facts, language ability, reasoning patterns, world model) is learned almost entirely during **pretraining**, from the massive raw text corpus. This is where the model "learns what it knows."
- **Behavior/style** (how to format a helpful response, follow instructions, adopt a conversational tone, refuse unsafe requests, structure an answer) is largely a matter of **surface-level alignment**, learned during fine-tuning/alignment — teaching the model *how to present and use* the knowledge it already has, rather than teaching it new facts.

**The LIMA finding (Zhou et al., "LIMA: Less Is More for Alignment"):** The paper showed that a strong pretrained base model, fine-tuned on just **~1,000 carefully curated, high-quality instruction-response examples** (no RLHF at all), could produce responses competitive with models fine-tuned on orders of magnitude more data.

**The "Superficial Alignment Hypothesis"** (LIMA's central claim): a model's knowledge and core capabilities are learned almost entirely during pretraining; fine-tuning/alignment mainly teaches the model the **format, style, and behavior** for interacting with users — *not* new knowledge. This implies you don't need millions of fine-tuning examples for good alignment — you need a **small, extremely high-quality, diverse set** that clearly demonstrates the desired behavior/style, because the underlying knowledge is already there from pretraining.

**Practical/interview implication:** This is why "quality over quantity" is a common mantra for instruction-tuning datasets, and why the biggest lever for base capability is still pretraining data/scale — fine-tuning mostly steers/unlocks the existing capability rather than injecting new knowledge. (Caveat worth mentioning: this doesn't mean fine-tuning can teach *zero* new facts — it can, to a limited extent — but it's a far less efficient/reliable way to add knowledge compared to pretraining or retrieval/RAG.)

## 17. Alignment Techniques in LLMs

**Goal of alignment:** make the model's outputs helpful, honest, and harmless — matching human values/preferences — beyond just "predict plausible next token" or "follow instructions literally."

### 17.1 RLHF (Reinforcement Learning from Human Feedback)
Classic 3-stage pipeline (used for ChatGPT-style models):

1. **SFT (Supervised Fine-Tuning):** start from a pretrained base model, fine-tune on high-quality human-written (prompt, ideal response) pairs → produces an initial instruction-following policy.
2. **Reward Model (RM) training:** collect multiple model responses to the same prompt, have human labelers **rank** them (best to worst). Train a separate reward model to predict a scalar "quality score" that matches human rankings (usually trained with a pairwise ranking loss, e.g., Bradley-Terry style: reward(chosen) should be higher than reward(rejected)).
3. **RL fine-tuning (usually PPO — Proximal Policy Optimization):** use the reward model as the "reward signal" and fine-tune the SFT model with reinforcement learning to maximize expected reward, while a **KL-divergence penalty** keeps the policy from drifting too far from the original SFT model (prevents "reward hacking" / degenerate outputs that game the reward model but are actually bad).

**Why RLHF works:** It's often easier for humans to *compare/rank* two responses ("which is better?") than to *write* the perfect response from scratch, so ranking-based feedback scales better and captures nuanced human preferences (tone, helpfulness, safety) that are hard to specify with rules.

**Downsides of RLHF:** complex 3-model pipeline (policy, reward model, and often a frozen reference model for KL penalty), RL training is unstable and hyperparameter-sensitive, expensive to run, and reward models can be "hacked" (policy finds outputs that score high on the reward model but aren't actually good).

### 17.2 DPO (Direct Preference Optimization)
DPO simplifies RLHF by **removing the separate reward model and RL loop entirely**. It reframes preference learning as a simple, direct supervised-learning-style loss on the human-preference pairs (chosen response vs rejected response), derived mathematically to have the *same optimal solution* as the RLHF objective but without needing to train an explicit reward model or run unstable RL.

**Intuition:** Instead of "train a reward model, then use RL to maximize it," DPO directly increases the model's probability of generating the *preferred* response and decreases probability of the *rejected* response (relative to a reference/frozen copy of the SFT model), using a loss function grounded in the same underlying Bradley-Terry preference theory as RLHF.

**Why DPO is popular:** Much simpler to implement (just a modified cross-entropy-like loss on paired preference data), more stable/reproducible than PPO-based RLHF (no RL instability), cheaper (no separate reward model or multiple rounds of sampling), and empirically competitive with RLHF quality on many benchmarks — this is why many recent open models (and increasingly production systems) have shifted to DPO or DPO-variants.

**RLHF vs DPO — quick comparison:**
| Aspect | RLHF (PPO-based) | DPO |
|---|---|---|
| Reward model | Separate model, trained explicitly | Not needed (implicit in the loss) |
| Training loop | RL (online, samples from policy) | Supervised-style (offline, on static preference pairs) |
| Stability | Can be unstable, many hyperparameters | More stable, simpler |
| Compute cost | High (multiple models + RL rollouts) | Lower |
| Data needed | Preference pairs + RL environment | Preference pairs only |

## 18. PEFT (Parameter-Efficient Fine-Tuning)

**Motivation:** Full fine-tuning of a multi-billion parameter model requires storing gradients and optimizer states (e.g., Adam needs 2 extra copies of every parameter) for *every* parameter — memory cost can be 4-6x the model size, making it infeasible on consumer/limited hardware, and you'd need a full separate copy of the model per task/customer. PEFT methods freeze the (huge) pretrained model and only train a small number of *additional* or *selected* parameters.

### 18.1 LoRA (Low-Rank Adaptation)
**Core idea:** Instead of updating a large weight matrix `W` (shape `d × k`) directly during fine-tuning, freeze `W` entirely and learn a small "update" as the product of two much smaller low-rank matrices:
```
W_new = W_frozen + (A · B)   where A is (d × r), B is (r × k), and r << d, k
```
`r` (the **rank**) is typically very small (e.g., 4, 8, 16, 64) compared to the original dimensions (which can be in the thousands).

**Why this works (intuition):** The hypothesis (backed empirically) is that the *change* needed in weights to adapt a pretrained model to a new task has a low "intrinsic rank" — i.e., you don't need to move the weights in every possible direction, just a small, task-specific subspace of directions. So a low-rank approximation of the update is often sufficient to capture the needed adaptation.

**Benefits:**
- Massively fewer trainable parameters (often <1% of the full model) → far less GPU memory needed for gradients/optimizer states, faster training.
- The original weights `W` never change — so you can keep one frozen base model and just swap in different small LoRA adapters (a few MB each) for different tasks/customers, instead of storing a full fine-tuned copy per task.
- At inference, `A·B` can be merged back into `W` (since it's just addition), so there's **zero extra inference latency** compared to the original model, if you choose to merge.
- Typically only applied to specific weight matrices (commonly the attention Q and V projection matrices) rather than every single weight, further saving compute.

### 18.2 QLoRA (Quantized LoRA)
QLoRA combines quantization (Section 15) with LoRA to push efficiency even further: the **frozen base model is quantized down to 4-bit precision** (using a specialized format like NF4 — "4-bit NormalFloat," designed to be information-theoretically optimal for normally-distributed weights), while the small **LoRA adapters are kept/trained in higher precision** (e.g., BF16).

**Key innovations in QLoRA (worth naming in interviews):**
- **4-bit NormalFloat (NF4)** quantization — a quantization scheme tuned specifically for the typical (roughly normal) distribution of neural network weights, more accurate than naive uniform 4-bit quantization.
- **Double quantization** — quantizing the *quantization constants themselves* to save a little extra memory.
- **Paged optimizers** — using NVIDIA unified memory to gracefully handle occasional GPU memory spikes during training, avoiding out-of-memory crashes.

**Result:** QLoRA made it possible to fine-tune a 65B-parameter model on a *single* 48GB GPU (previously would have required multiple 80GB+ GPUs for full fine-tuning) — a huge democratization of LLM fine-tuning, and now the default recipe for fine-tuning open LLMs on limited hardware.

**Other PEFT methods worth a one-liner:**
- **Adapters:** small trainable bottleneck feed-forward modules inserted between existing frozen Transformer layers.
- **Prefix-tuning / Prompt-tuning:** freeze the whole model and only learn a small set of continuous "virtual token" embeddings prepended to the input, steering the model's behavior without touching its weights at all.

## 19. Hallucination

**What is it?** Hallucination is when an LLM generates text that is fluent and confident-sounding but **factually incorrect, fabricated, or unsupported** by its training data or any provided context — e.g., citing a paper that doesn't exist, inventing a statistic, or misattributing a quote.

**Why does it happen? (root causes)**
1. **The training objective doesn't optimize for truth** — the model is trained to predict the statistically likely next token, not to verify facts. Plausible-sounding text and true text are not the same target.
2. **Gaps/errors/bias in training data** — if the training corpus doesn't contain the fact, contains conflicting info, or contains misinformation, the model has no reliable ground truth to draw from.
3. **Compression and interpolation** — the model compresses trillions of tokens into a limited number of parameters; on rare/specific facts (e.g., a specific person's birthday, an exact citation), it may "blend" or "interpolate" between similar-looking facts it has seen, producing a plausible but wrong answer.
4. **Lack of grounding at inference time** — without access to real-time or verified external data, the model can only rely on what's baked into its weights (parametric memory), which is fixed at training time and inherently lossy.
5. **Decoding randomness** — sampling-based decoding (temperature, top-p) can push the model toward lower-probability, less-grounded continuations, increasing hallucination risk (though even greedy decoding hallucinates).
6. **Overconfidence from RLHF/alignment training** — alignment sometimes optimizes models to sound helpful/confident, which can inadvertently reward confident-sounding wrong answers over honest "I don't know" answers if that wasn't specifically trained for.

**Types of hallucination (a useful taxonomy for interviews):**
- **Intrinsic hallucination:** the output directly contradicts the given source/context (e.g., in a RAG/summarization task, the model's summary contradicts the source document it was given).
- **Extrinsic hallucination:** the output adds information that is neither supported nor contradicted by the given source — it's simply *not present* in the source (harder to catch, since it's not a direct contradiction).
- **Factual hallucination:** the model states something about the world that is objectively false (independent of any provided context) — e.g., wrong historical dates, wrong scientific facts.
- **Faithfulness hallucination:** specific to summarization/RAG — the output deviates from what the *given source material* actually says, even if the claim itself might be true in general.

**How to reduce/mitigate hallucination (practical, and directly relevant to Sourav's RAG/LLM-eval work):**
- **RAG (Retrieval-Augmented Generation):** ground the model's answer in retrieved, verifiable documents (e.g., FAISS-based retrieval) rather than relying purely on parametric memory — dramatically reduces hallucination on knowledge-intensive queries, and lets you cite sources.
- **Prompting techniques:** explicitly instruct the model to say "I don't know" when uncertain, ask it to cite sources, or use chain-of-thought prompting to encourage more careful reasoning before answering.
- **Fine-tuning/alignment for honesty:** train specifically on examples that reward calibrated uncertainty and penalize confident fabrication (rather than only rewarding "sounding helpful").
- **Lower temperature / more constrained decoding** for factual tasks (reduces randomness-driven drift, though doesn't eliminate hallucination from bad parametric knowledge).
- **Self-consistency / ensembling:** generate multiple answers (e.g., via different sampling runs) and check for agreement — disagreement is a signal of low confidence/potential hallucination.
- **External fact-checking / verification layers:** post-hoc verify claims against a trusted knowledge base or search engine before presenting the answer to the user.
- **Better evaluation and monitoring in production:** exactly the kind of LLM-evaluation pipeline (async, FAISS-backed RAG evaluation, drift monitoring) that catches hallucination patterns at scale before they reach end users.

## 20. LLM Evaluation Metrics

### 20.1 Perplexity
Perplexity measures how "surprised" a language model is by a given text — it's the exponentiated average negative log-likelihood the model assigns to the true tokens:
```
Perplexity = exp( - (1/N) * Σ log P(w_t | w_1, ..., w_(t-1)) )
```
- **Lower perplexity = better** — it means the model assigned higher probability to the actual next tokens, i.e., it was less "surprised"/more confident about the correct continuation.
- Intuition: perplexity roughly represents "the effective number of equally-likely choices the model was choosing among at each step" — a perplexity of 20 means the model was, on average, as uncertain as if it were picking uniformly among 20 options.
- **Limitation:** perplexity measures how well the model predicts held-out *text* (a proxy for fluency/language modeling quality), but it does **not** directly measure factual correctness, helpfulness, safety, or reasoning ability — a model can have low perplexity on a domain while still hallucinating or giving unhelpful answers. It's mainly used to compare pretraining/base-model quality, not to evaluate instruction-following/chat quality.

### 20.2 Other important evaluation metrics
- **BLEU / ROUGE / METEOR:** n-gram overlap-based metrics originally from machine translation (BLEU) and summarization (ROUGE) — compare generated text against reference text(s) via overlapping word/phrase sequences. Fast and cheap, but penalize valid paraphrases and don't capture semantic correctness well.
- **BERTScore:** uses contextual embeddings (from a BERT-like model) to compute semantic similarity between generated and reference text at the token level, rather than exact n-gram overlap — better at recognizing paraphrases than BLEU/ROUGE.
- **Exact Match (EM) / F1:** common for extractive QA tasks — EM checks if the predicted answer exactly matches the reference; F1 gives partial credit based on token overlap.
- **Task-specific accuracy/benchmarks:** e.g., MMLU (broad knowledge/reasoning across subjects), HellaSwag (commonsense reasoning), HumanEval/MBPP (code generation correctness via unit tests), GSM8K (grade-school math reasoning) — standard public benchmarks used to compare general LLM capability.
- **LLM-as-a-judge:** use a strong LLM (e.g., GPT-4-class model) to *rate or compare* two responses for helpfulness/correctness/style, often against a rubric — scales much better than pure human evaluation and correlates reasonably well with human judgment, though it has its own biases (e.g., favoring longer or more confidently-worded answers) that need to be controlled for.
- **Human evaluation:** the gold standard for helpfulness/safety/preference — humans rate or rank responses (as in RLHF data collection) — expensive/slow but most reliable for subjective quality.
- **Faithfulness/groundedness metrics (RAG-specific):** measure whether a generated answer is actually supported by the retrieved context — critical for hallucination detection in RAG pipelines (e.g., using an NLI-style entailment model to check if the source "entails" the generated claim).
- **Latency, throughput, cost metrics:** production-relevant, non-quality metrics — tokens/sec, time-to-first-token, cost-per-1K-tokens — critical for real-world deployment decisions, exactly the kind of thing tracked in a production LLM evaluation system (e.g., 500+ evaluations/day at ~2-second latency).
- **Calibration:** how well a model's stated confidence matches its actual accuracy — a well-calibrated model that says "I'm 90% sure" should be right about 90% of the time; poor calibration is closely tied to hallucination risk.

## 21. Other Important Topics Relevant to LLMs

- **RAG (Retrieval-Augmented Generation):** combine an LLM with a retrieval system (e.g., FAISS/Pinecone/Weaviate vector search over a document corpus) — retrieve relevant chunks at query time, inject them into the prompt as context, and let the LLM generate a grounded answer. Reduces hallucination, keeps knowledge up-to-date without retraining, and enables citation of sources. Key components: chunking strategy, embedding model choice, vector index/search (ANN algorithms like HNSW), reranking, and prompt construction.
- **Chain-of-Thought (CoT) prompting:** prompting the model to "think step by step" before giving a final answer, which measurably improves performance on multi-step reasoning/math tasks — an emergent capability that shows up mainly in sufficiently large models.
- **In-context learning / few-shot prompting:** providing a handful of example (input, output) pairs directly in the prompt lets the model infer the task pattern without any weight updates.
- **Mixture of Experts (MoE):** an architecture where only a subset of specialized "expert" sub-networks are activated per input token (via a learned routing/gating mechanism), allowing models to have a very large total parameter count while keeping the actual compute cost per token much lower (sparse activation) — used in models like Mixtral.
- **Model distillation:** train a smaller "student" model to mimic a larger "teacher" model's outputs (soft probability distributions, not just hard labels) — produces a much smaller, faster model that retains much of the teacher's quality.
- **Catastrophic forgetting:** when fine-tuning on a new task causes the model to lose previously learned general capabilities — a key risk of full fine-tuning, mitigated by PEFT, replay of general data, or careful learning-rate/regularization choices.
- **Agentic LLMs / tool use / function calling:** LLMs that can call external tools/APIs (search, calculators, code execution, databases) as part of generating a response, enabling multi-step autonomous task completion beyond pure text generation.
- **Model drift / monitoring in production:** since real-world input distributions shift over time, production LLM systems need drift detection (directly relevant to Sourav's Model Health Score work — PSI, KS-test style checks can be adapted to monitor embedding or output distributions of LLM systems too).
- **Guardrails / safety filters:** input/output content filtering layers (prompt injection detection, PII redaction, toxicity/safety classifiers) wrapped around raw LLM calls in production systems.
- **Context length vs retrieval trade-off:** as context windows grow huge (1M+ tokens), there's an active debate on "just stuff everything into context" vs "retrieve only what's relevant" — very large context is more expensive and suffers from "lost in the middle," so smart retrieval often still beats brute-force long context for accuracy and cost.

## 22. Simple Illustrative Code Example

A minimal, from-scratch **character-level bigram language model** in PyTorch — small enough to run instantly, but it demonstrates the exact same core idea as GPT: an embedding table predicting "next token" probabilities, trained with cross-entropy loss, and generating text autoregressively (sampling one token at a time and feeding it back in). This is essentially "GPT with the Transformer layers removed," which makes the core language-modeling concept crystal clear before adding attention.

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

# ---- 1. Toy corpus & tokenizer (character-level, similar spirit to BPE/WordPiece but simplest possible) ----
text = "large language models learn to predict the next token"
chars = sorted(list(set(text)))
vocab_size = len(chars)
stoi = {ch: i for i, ch in enumerate(chars)}   # string -> integer (tokenization)
itos = {i: ch for ch, i in stoi.items()}       # integer -> string (detokenization)

encode = lambda s: [stoi[c] for c in s]
decode = lambda ids: "".join(itos[i] for i in ids)

data = torch.tensor(encode(text), dtype=torch.long)

# ---- 2. Bigram Language Model: an embedding table IS the "next-token" predictor ----
class BigramLanguageModel(nn.Module):
    def __init__(self, vocab_size):
        super().__init__()
        # each token directly maps to a row of logits over the whole vocabulary
        self.token_embedding_table = nn.Embedding(vocab_size, vocab_size)

    def forward(self, idx, targets=None):
        logits = self.token_embedding_table(idx)  # (batch, time, vocab_size)
        loss = None
        if targets is not None:
            B, T, C = logits.shape
            loss = F.cross_entropy(logits.view(B * T, C), targets.view(B * T))
        return logits, loss

    def generate(self, idx, max_new_tokens, temperature=1.0, top_k=None):
        # this loop IS the "decoding" step (Section 14) — autoregressive generation
        for _ in range(max_new_tokens):
            logits, _ = self(idx)
            logits = logits[:, -1, :] / temperature       # temperature scaling
            if top_k is not None:                          # top-k filtering
                v, _ = torch.topk(logits, top_k)
                logits[logits < v[:, [-1]]] = -float("inf")
            probs = F.softmax(logits, dim=-1)
            idx_next = torch.multinomial(probs, num_samples=1)  # sample, not argmax (greedy would be .argmax)
            idx = torch.cat((idx, idx_next), dim=1)         # teacher-forcing style append, but with model's OWN token (inference time)
        return idx

# ---- 3. Training loop (Section 12: next-token prediction via cross-entropy) ----
model = BigramLanguageModel(vocab_size)
optimizer = torch.optim.AdamW(model.parameters(), lr=1e-2)

block_size = 8  # a tiny "context window" (Section 9)
for step in range(500):
    ix = torch.randint(len(data) - block_size, (16,))
    x = torch.stack([data[i:i + block_size] for i in ix])
    y = torch.stack([data[i + 1:i + block_size + 1] for i in ix])  # y = x shifted by 1 (teacher forcing target)

    logits, loss = model(x, y)
    optimizer.zero_grad(set_to_none=True)
    loss.backward()
    optimizer.step()

print("Final training loss:", loss.item())

# ---- 4. Generation (decoding) ----
context = torch.tensor([[stoi["l"]]], dtype=torch.long)
generated = model.generate(context, max_new_tokens=40, temperature=0.8, top_k=5)
print(decode(generated[0].tolist()))
```

**What this tiny example maps to real LLMs:**
- `nn.Embedding` → the token embedding table (Section 10), scaled up massively and combined with positional encodings (Section 11) in real models.
- `F.cross_entropy` on shifted `(x, y)` pairs → exactly the next-token-prediction training objective (Section 12), and the shifted targets are the essence of teacher forcing (Section 13).
- `.generate()` loop → autoregressive decoding (Section 14) — here it shows temperature scaling, top-k filtering, and multinomial sampling explicitly.
- Missing piece vs. real GPT: no self-attention/Transformer blocks (Section 4) — a real model replaces the plain embedding lookup with many stacked attention + feed-forward layers so predictions depend on the *whole* preceding context, not just the immediately previous token (a true bigram model only looks 1 token back).

## 23. Common & Tricky Interview Questions — with Expert Answers

**Q1: Why do LLMs use decoder-only architectures instead of encoder-decoder, given GPT's success?**
> Decoder-only models are simpler (one stack instead of two), and because they're trained with the same causal/autoregressive objective at both pretraining and generation time, there's no train-test mismatch. They also scale very well and, empirically, have proven extremely capable at both understanding and generation when scaled up — you don't strictly need an encoder to "understand" if the decoder attends over the full prompt anyway (the prompt tokens are just earlier positions the causal mask still lets later tokens see).

**Q2: Why is self-attention O(n²), and why does that matter?**
> Every token computes an attention score against every other token, so for a sequence of length n, you get n×n pairwise interactions — both compute and memory scale quadratically. This is the fundamental reason long-context models are expensive and why techniques like FlashAttention, sparse/local attention, and efficient KV-caching exist — they attack this quadratic bottleneck directly.

**Q3: What's the difference between fine-tuning and prompting/in-context learning — when would you choose one over the other?**
> Fine-tuning permanently updates model weights using a training dataset — it "bakes in" new behavior/knowledge, is persistent across all future calls, but costs compute/data and risks catastrophic forgetting. Prompting/in-context learning gives instructions or examples at inference time with zero weight updates — cheap, instant, reversible, but limited by context window size and doesn't generalize beyond that single call. Rule of thumb: use prompting/RAG first for knowledge-grounding or task-steering; reach for fine-tuning (ideally PEFT) when you need consistent behavior/format/style at scale, or the task requires patterns that can't be captured concisely in a prompt.

**Q4: Why does BPE sometimes tokenize the same word differently depending on whether it has a leading space?**
> Because tokenizers like GPT-2's byte-level BPE treat the space character as part of the token itself (e.g., " the" and "the" are different byte sequences), so the model actually learns separate embeddings for word-with-leading-space vs word-without. This is a common source of confusing tokenizer behavior and subtle prompt-engineering effects (e.g., trailing spaces in a prompt can change tokenization and thus completion behavior).

**Q5: Why can LLMs struggle with simple tasks like counting letters in a word or reverse a string?**
> Because of sub-word tokenization — the model doesn't see individual characters, it sees whole sub-word chunks (e.g., "strawberry" might be 2-3 tokens, not 10 characters). Character-level operations require the model to reconstruct character-level information indirectly from training data patterns, which it's not naturally set up to do well. This is a direct, practical consequence of the tokenization choice (Section 8).

**Q6: What's the difference between temperature and top-p, and why use them together?**
> Temperature reshapes *how peaked or flat* the whole probability distribution is (a global rescaling), while top-p (nucleus sampling) dynamically restricts *which* tokens are even eligible to be sampled based on cumulative probability mass. They solve different problems: temperature controls "how much randomness," top-p controls "how much of the improbable tail to exclude." Using both together (e.g., temperature=0.7 + top_p=0.9) gives fine-grained control — top-p removes clearly bad low-probability options first, then temperature fine-tunes how randomly you sample among what's left.

**Q7: Explain why RLHF needs a KL-divergence penalty against the reference model.**
> Without it, the policy being optimized via RL could drift arbitrarily far from the original SFT model in pursuit of maximizing the reward model's score — potentially finding degenerate outputs that "game" the reward model (reward hacking) without actually being good responses (e.g., repeating flattering phrases the reward model over-scores). The KL penalty keeps the fine-tuned policy "close" to the original well-behaved SFT model, trading off some reward-maximization for staying grounded and fluent.

**Q8: How does DPO avoid needing an explicit reward model, mathematically/intuitively?**
> DPO is derived by showing that the optimal policy under the standard RLHF objective (maximize reward minus KL penalty) has a closed-form relationship to the reward function. By substituting this relationship back into the Bradley-Terry preference model, the reward model term cancels out algebraically, leaving a loss expressed purely in terms of the policy's own probabilities on the chosen vs rejected responses (relative to the frozen reference model). So DPO isn't "skipping" reward modeling conceptually — it's mathematically folding the implicit reward model directly into the policy's loss function, making a separate model and RL loop unnecessary.

**Q9: What's the difference between LoRA and full fine-tuning in terms of what the model can actually learn — are there tasks where LoRA falls short?**
> LoRA assumes the necessary weight update has a low intrinsic rank, which holds well for most task adaptation (style, format, domain steering, following new instructions). But for very large distributional shifts — e.g., trying to teach entirely new capabilities, a new language the base model has near-zero exposure to, or extensive new factual knowledge — a low-rank update may not have enough capacity, and full fine-tuning (or extensive continued pretraining) can outperform LoRA. In practice, choice of rank `r` and which layers to target also significantly affects this ceiling.

**Q10: If perplexity is low, does that mean the model is a good chatbot? Why or why not?**
> No. Perplexity only measures how well the model predicts the statistical patterns of held-out *text*, i.e., raw language-modeling fluency. It says nothing about factual correctness, helpfulness, following instructions, safety, or reasoning quality — a model can be extremely fluent (low perplexity) while confidently hallucinating or being unhelpful. That's exactly why chat/instruction-tuned models are evaluated with task-specific benchmarks, human preference data, or LLM-as-a-judge instead of relying on perplexity alone.

**Q11: Why does hallucination happen even in very large, well-trained models — isn't more scale supposed to fix it?**
> Scale improves general capability and reduces some hallucination, but it doesn't fix the root cause: the training objective (next-token prediction) rewards *plausible* text, not *verified true* text, and the model has no built-in mechanism to distinguish "I actually know this" from "this sounds right based on patterns." Rare/long-tail facts are especially prone to this because the model has seen too little signal to represent them precisely (vs. interpolating from similar-looking facts). This is exactly why grounding techniques like RAG, and alignment specifically targeting calibrated honesty, matter more than raw scale alone for reducing hallucination.

**Q12: In a production RAG + LLM evaluation system (e.g., evaluating agent conversations at scale), what are the main failure modes you'd watch for, and how would you catch them?**
> Key failure modes: (1) retrieval failure — relevant context wasn't retrieved at all (bad chunking/embedding/index issue), (2) faithfulness failure — the LLM's answer isn't actually grounded in the retrieved context even though the context was correct (a hallucination on top of good retrieval), (3) latency/throughput degradation under load, (4) distributional drift in incoming queries or documents over time (analogous to concept drift — this is where KS-test/PSI-style monitoring, applied to embedding distributions or evaluation-score distributions, becomes directly useful), and (5) evaluation metric drift itself — e.g., an LLM-as-a-judge model changing behavior after an upstream model update. A good production evaluation pipeline instruments each of these separately (retrieval-quality metrics, faithfulness/groundedness scoring, latency/error-rate dashboards, and periodic drift checks) rather than relying on one end-to-end quality score.
